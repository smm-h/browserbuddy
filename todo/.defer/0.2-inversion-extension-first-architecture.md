# BrowserBuddy 0.2 — the inversion: extension-first architecture

Status: design complete, all decisions locked, awaiting an explicit implementation imperative. This file is the full design record of a deep decision round. No design work remains open inside it (a few items are flagged "verify empirically" — those are runtime confirmations, not unresolved forks).

---

## 1. Context

BrowserBuddy 0.1.0 (released) is structured **server-first**: the npm package is the product and holds all intelligence (event store, demo cleaning, MCP tool surface); the extension is a thin observer + RPC executor that streams everything to a local WebSocket hub on `127.0.0.1:8590`. Without the running server, the extension does nothing.

A vision statement proposed **inverting** this: make the *extension* the product — one-click installable from the Web Store / AMO, working standalone with its own GUI, history, and replayable demonstrations stored inside the extension — and demote the server to an optional, session-scoped **bridge** that lets Claude (or another client) attach to watch and drive. A browser with no agent attached becomes a normal working state; the AI is an enhancement, never a requirement. Because the always-on component is the extension (not a standing server), there is no privileged process to secure.

This todo captures the accuracy grading of that statement and every design decision made resolving it.

### 1a. How accurate was the vision statement (grading against 0.1.0)

Mostly inaccurate **as a description of what exists** (it describes an inversion of the current build), but a coherent **destination**. Claim by claim:

- "Product is the extension, not the MCP" — inverted today; all intelligence is server-side.
- "One-click install from Web Store/AMO" — false; Chrome needs load-unpacked, Firefox runs it as a temporary add-on that vanishes on restart. No store presence.
- "Works standalone: GUI to record/replay/run" — false; extension has no UI beyond a badge, no storage beyond a reconnect buffer, no replay engine.
- "History and demos stored in the extension, exportable" — false; both live server-side in `server/data/`.
- "MCP server is an optional, session-scoped bridge" — half true; the server already is session-scoped and the extension already treats its absence as normal (reconnect ladder, buffering, badge), but "optional" is false today (no server = no product).
- "No privileged process, no auth needed" — directionally right, but **"no auth needed" is wrong even as a destination**: today the extension dials an unauthenticated `ws://127.0.0.1:8590`, so any local process that squats the port can impersonate the hub and drive the logged-in browser. The inversion shrinks the surface; the bridge still needs an auth story. See §4 (transport) — the chosen design makes the security boundary the OS user, honestly.
- "Two replay forms (deterministic + agent-authored parameterized)" — neither exists today; current replay is agent-mediated only.
- "Open details: split, permissions, GUI-action attribution, locators" — accurate and incomplete; also open were bridge pairing/auth, version skew, store-review friction.

**What survives the inversion unchanged** (why this is cheap relative to a rewrite): the wire protocol shape, the observation pipeline, redaction-at-source (already extension-side — correctly on the right side of the split), actor attribution, and the selector strategy.

---

## 2. Target architecture (north star)

- **The extension is the product and the sole semantic component.** It owns: event schemas, history storage, the Action model, redaction, the MCP tool definitions and dispatch, and a deterministic replay engine — all in the extension, working standalone.
- **The external component is a domain-blind pipe** that carries opaque messages and never needs updating. Its only knowledge is MCP lifecycle framing; it knows nothing about browsers, events, Actions, or redaction. A tripwire test (mirroring the existing stdout-purity tripwire) asserts zero product vocabulary in it.
- **The AI is optional.** No attached agent is a normal state. The extension records, replays, and manages Actions on its own; an attached client enriches (smarter, parameterized, self-repairing replay) but is never required.
- **Skew is structurally minimized** by having exactly one component with semantics. See §4 (version skew).

---

## 3. Named hard invariants (carry forward + one new)

Existing (preserved): stdout is MCP-reserved (stderr-only diagnostics); hard errors, never silent fallbacks; redaction is a guarantee, sensitive values never leave the page; actor attribution is sacred (agent actions never recorded as user); `docs/PROTOCOL.md` is the normative wire contract; the extension binds `ext`, never shadows `chrome`; no build step for the extension core.

**New invariant — "absence must be observable."** Whenever something cannot be done, the system emits a visible marker/error, never a silent gap. This principle recurs across the design and should be listed alongside redaction and attribution:
- ungranted-site observation → explicit `not_observed` marker events (not silence);
- second-browser attach collision → visible rejection (not silent takeover);
- replay locator miss → pause/hard-stop/*logged* auto-heal (never a silent best-guess);
- protocol/version mismatch → hard refusal with an actionable message.

## 4. Decisions locked (by cluster)

### Transport & process topology

**Chosen: solution #6 — browser-spawned native host serving Streamable-HTTP MCP.**
- The extension calls `chrome.runtime.connectNative(...)`; the **browser spawns the native host** and owns the stdio pipe to it. The **host** (a normal OS process, so it may listen) binds `127.0.0.1:<ephemeral>` and serves Streamable-HTTP MCP with a bearer token. Claude dials that HTTP endpoint. **The extension never binds a socket** — the listener is always the host.
- The host **writes Claude's MCP config itself** (live port + token), so user setup collapses to one click in the GUI ("Connect") + restart the agent.
- **Why #6 over the alternatives:**
  - vs #4 (unix-socket rendezvous — the earlier tentative pick): #6 is *more* cross-platform, not less. Loopback HTTP sidesteps AF_UNIX `sun_path` length limits, macOS `$TMPDIR` path quirks, and the Windows named-pipe DACL problem (which would otherwise force a non-Node host). Same security/endgame benefits.
  - vs #1 (hardened WebSocket only): #1 keeps two semantic components, the lifetime inversion, and the SW-teardown-mid-RPC risk; caps short of the empty-bridge endgame.
- **Security posture:** eliminates port-squatting/impersonation (ephemeral port + bearer token; the host is browser-authenticated to the listed extension IDs). Trust boundary = the OS user account — the same boundary that already protects the browser profile on disk. A same-user attacker can already read the cookie jar, so nothing weaker-than-user is worth armoring; nothing stronger-than-user is achievable for same-user processes. This is the SSH-agent / GPG-agent / Wayland-socket norm. Document the threat model plainly; do not claim "no auth needed" without this framing.
- **Fixes the lifetime inversion:** today the session-scoped (Claude-spawned) side listens and the always-on (browser) side dials — backwards, and the root of the reconnect ladder and the "disconnected is normal" badge. Under #6 the always-on host owns the endpoint; the session-scoped agent dials.
- **Multi-client:** Streamable HTTP is natively multi-client, so N agent sessions attach without arbitration.

**Bridge statefulness: fully stateless.** The external component is a pure protocol translator — zero state, restart-safe, trivially correct. `server/src/store.js` (ring buffer + JSONL) largely dies or moves into the extension. Even lockstep waiting is held extension-side.

**Endgame & the rejected/deferred rungs (from a 10-solution topology exploration):**
- **#8 (semantically empty bridge)** is the endgame the above enables — all MCP tool definitions/dispatch live in the extension; the npm/host artifact is a dumb pipe. Because MCP tool discovery is dynamic (`tools/list` + `list_changed`), extension-owned tools propagate at runtime with no version coupling to the pipe.
- **#7 (extension carries its own store-delivered host)** — *deferred, not rejected.* Its **goal** (host as a mere resource of the extension, auto-updated through the store, not independently versioned) is the north star. Its **mechanism** (ship host bytes in the extension, one-gesture installer that writes executables, self-replace on update) is deferred past 0.2 on cost (per-platform signing/notarization/SmartScreen) and store-policy risk (reviewers scrutinize extensions that drop executables).
- **#8-relay (zero-local-footprint E2E-encrypted relay)** — *retained as an explicit opt-in transport*, never the default (a network hop + hosted service is wrong as the baseline for a local-browser product; privacy optics even with E2EE). Legitimate under "explicit mode selection is fine."
- **#9 (bridge as an Isolated Web App via Direct Sockets)** — *mechanism rejected* (Chrome/Edge only; Firefox has no equivalent; no consumer IWA distribution channel), but its "push for a platform capability" spirit is redirected into the capability request (§10).
- **#10 (dissolve the premise — in-extension agent loop)** — *rejected wholesale.* It abandons BrowserBuddy's thesis ("the coding agent you already use attaches to your browser"), becomes a competitor to Comet/Atlas/Claude-in-Chrome, and drags the agent under MV3 lifetime limits + store review for prompt changes.
- **Migration path is monotone:** the rungs share one internal seam — an MCP-lifecycle shim over an opaque JSON-RPC duplex. Graduating between topologies is a transport swap, not a rewrite. Nothing built at #1/#3 is thrown away at #6/#8.

### Protocol

- **Target the MCP `2026-07-28` "stateless core" spec.** Notable changes it brings: protocol sessions removed; the `initialize`/`initialized` handshake removed (metadata rides in `_meta` on every request); **`server/discover`** RPC mandatory; **`subscriptions/listen`** as the first-class server→client push channel; **MRTR (Multi Round-Trip Requests)** replaces all server-initiated requests (sampling/elicitation/roots); SSE resumability removed; Sampling/Roots/**Logging deprecated** (Logging's recommended replacement is *stderr* — already our invariant).
  - **Adopt:** `subscriptions/listen` for pushing live browser events over the existing connection; `server/discover`; `resultType` on results; `ttlMs`/`cacheScope` + deterministic tool order on `tools/list`.
  - **Evaluate MRTR as the implementation of `browser_wait_for_user`** — MRTR is now the protocol-native shape for "pause and wait for the human," and may fit lockstep better than a blocking tool call.
  - **Verify-first caveat:** Claude Code's currently-negotiated revision is unconfirmed. Keep the `initialize` handshake / compat probe until a runtime check confirms Claude Code speaks `2026-07-28` (`server/discover` is the probe). Do **not** drop `initialize` blind.
- **Protocol version = its own monotone integer, independent of both marketing versions**, and **derive it from a hash of the machine-readable schema** so "forgot to bump" is unrepresentable. Send both the protocol integer and the artifact version at handshake; **only the integer gates**. (Stores force involuntary extension version bumps on metadata resubmissions, so keying compat to marketing versions self-sabotages.)
- **Version-skew policy (the store collides with no-backward-compat):** the auto-updating extension speaks **current + previous** protocol; the bridge **never** speaks an old extension's protocol. One-sided, time-boxed, documented in `docs/ARCHITECTURE.md` as a **narrow, store-forced exception** to the project's no-compat rule — explicitly not precedent for ordinary compat creep. Unknown-message policy differs by direction (falls out of side-effects): an unknown **event** is recorded with an explicit `unknown` marker (nothing lost, absence observable); an unknown **RPC method** is a hard error naming the method and the version gap.
- **Release orchestration:** **npm leads, stores trail.** A protocol-touching release publishes npm immediately; the extension carries the compat window; stores approve on their own clock. Server-only (protocol-untouched) releases ship freely. rlsbl growing CWS/AMO upload+status pipelines is a later, orthogonal upgrade (correct long-term tooling), not required for 0.2.

### Identity & multi-attach

- **Per-install identity = (browser, profile).** Each profile is a separate extension install with its own storage (own history, Actions, seq counter). With native messaging, each profile's extension instance spawns its own host process — so per-install identity falls out of the transport for free.
- Each install generates a **UUID + user-editable label** ("Work", "Personal", "FF-testing") in the GUI. Identity = the install, not the browser.
- Each host binds its own endpoint under a per-install path; **discovery is a directory read**, no registry, no pairing ceremony.
- **MCP tools gain an optional target** addressing label/id. With exactly one install attached (the common case), zero config. With several and no target: **hard error naming the candidates** — the agent picks, visibly. `browser_state` lists attached installs.
- Per-profile storage separation is a **feature** (work/personal never mix; sharing is deliberate export/import), not an accident.

### Event model & seq

- **Extension-owned, persistent seq** — monotonic per install, survives restarts of everything; `browser_observe` `sinceSeq` becomes stable across sessions ("everything since I last looked" works across days). (Time-ordered ULIDs considered and rejected — breaks the existing tool contract for modest gain.)

### Privacy & observation

- **Observation posture is a mandatory first-run mode choice** (no pre-selected default, mirroring the project's no-implicit-defaults philosophy): volatile-only / persist-when-armed / always-persist. Changeable anytime in settings. The extension captures nothing until the user picks.
- **Attach disclosure = full retained history.** The compensating controls live at the capture/retention side, not attach-time filtering:
  - one-click **observation pause** (badge-reflected),
  - a **history browser** (transparent timeline; inspect, select ranges/sites, delete selection, delete all),
  - a **"delete last N minutes"** control (the realistic "oops, didn't want that retained" affordance).
  - Consent is continuous at capture time, once at attach time.
- **Retention & controls:** configurable retention (age/size), a **never-observe origin list**, purge by site/range, manual demo/Action **export/import**. **No `storage.sync`** (demo/Action content includes page text — must not leave the machine via vendor clouds). **No incognito operation.**

### Permissions & distribution

- **Optional host permissions.** Base install = `activeTab` + storage; the user grants "observe everywhere" in one click, or per-site. On ungranted sites, emit explicit **`not_observed` marker events** (absence observable) rather than silently missing events. Store-review-friendlier than mandatory `<all_urls>`, and philosophy-consistent. Chrome and Firefox may warrant different defaults (Firefox already treats host permissions as opt-in).
- The current extension needs a minimal options/listing surface to be store-listable; **de-risk store review early** by submitting the current extension (with honest `<all_urls>` justification or the optional-perms model) *before* the GUI arc, to get the actual gatekeeper's permission-model feedback while it's cheap and to start the review-history clock.

### The Action model (unified record/replay/skill)

- **One unified `Action` type.** GUI recording and agent authoring produce the *same object*. Provenance field tracks `recorded` / `agent-authored` / `agent-repaired`. One replay engine, one run-journal. Standalone recording fully works without an agent; agents enrich/parameterize/repair the same object. (This subsumes the old separate "demo" vs "action" and the "skills" question.)
- **Actions are data, never code.** A step-list interpreted by the shipped engine — never agent-authored executable code. This is a hard line: remotely-authored code executing with extension privileges is exactly what CWS remote-code policy prohibits; agent-authored data is fine. It decides the Action format.
- **Parameterization:** named parameter slots the GUI prompts for at run time; agents mark which captured values are parameters.
- **Locator bundles (schema).** Each step stores css + visible text + ARIA role/accessible-name + nearby label + attributes; replay resolves by **priority vote**, using the first that uniquely matches. Strictly more robust than today's single uniqueness-checked selector, and standalone (agentless) replay has real fallbacks. **Decide/land early** — this schema rots with every recorded Action.
- **`on_failure` policy, per-action** (chosen at creation, changeable):
  - `hard_stop` — abort naming the failed step + what it sought;
  - `pause_and_ask` (**default**) — halt, highlight candidates, whoever's driving picks; offer to heal the stored locator. Redacted values prompt the same way (masked input, used once, never stored);
  - `auto_heal` — best-match and continue, **but must emit a visible healing event** into the run-journal ("step 4 locator missed; matched `<el>` by role+text vote"). Silent best-guessing stays banned; *logged* best-guessing is a legitimate per-action opt-in.
  - Interaction: `pause_and_ask` means "ask whoever's driving" — human in GUI, or the attached agent (which reads the failure and repairs via `action_update`). With nobody driving (unattended), it degrades to `hard_stop` + journal entry.
- **Run journal.** Every run records outcome, failed step, locator attempted, what the page offered instead, timestamp — stored with the Action, exposed through MCP. This creates the repair loop: standalone run fails at step 4 → failure sits in the journal → next agent attach reads it, inspects the live page, patches the Action.
- **MCP surface shifts** from demo-centric (`demo_record_start/stop/list/get`) to Action-centric (`action_create`/`action_update`/`action_list`/`action_get`/`action_run` + journal access). Exact tool names TBD at implementation, consistent with the unified model.

### Actor taxonomy (schema)

- **Add a third `replay` actor.** Three actors: `user` / `agent` / `replay`. Deterministic playback is `replay` however triggered (GUI or agent); GUI management clicks are `user`; agent-improvised live actions stay `agent`. Replay events appear in history but are **excluded from Action capture** (the recursion guard — replaying an Action must not record a new Action of itself — falls out naturally). (Structured initiator×mechanism provenance considered and deferred — value not needed until scheduling/multi-agent lands.)

### GUI

- **Side panel, vanilla no-build.** Chrome `sidePanel` / Firefox sidebar, hand-rolled vanilla JS components — **preserves the no-build-step invariant**. A glanceable persistent surface fits "shared space" better than a dismiss-on-click-away popup. Surfaces: record controls, Action list, history browser (select/delete), replay status, connection state, per-install label, observation-mode + pause. (A bundler-for-GUI-only was considered and rejected for 0.2 — revisit only if GUI ambition visibly outgrows vanilla.)
- **Standalone run scope: replay-only** (records/replays/manages/exports Actions). No ad-hoc action palette, no GUI eval, in 0.2 (self-XSS surface + review bait). Agent-driven actions are unaffected.

### Security (folds into 0.2)

- The live 0.1.0 defect (unauthenticated hub streams browsing events to any local connection on `127.0.0.1:8590`) is **fixed as part of the 0.2 topology rework**, not a separate 0.1.x patch. The #6 bearer-token/host-authenticated design closes it. (Rationale: the pairing/token work is reused by #6, so no throwaway; and 0.2 is the coherent place for it. Note this leaves the released 0.1.0 with a known loopback-only, same-user exposure in the interim — acceptable given near-zero adoption and the short gap.)

### Migration

- **Clean break, no migration tooling.** 0.1.0 shipped essentially pre-adoption, so there is no accumulated user data to carry across the inversion. Document a one-line manual export for the theoretical early adopter; let the old event-log history die with the old architecture (it was always a rolling window in spirit). Revisit only if real usage accumulates before 0.2 lands.

## 5. Implementation sequencing (suggested phases)

The design supports incremental delivery; nothing below forces a rewrite of anything above it.

1. **Protocol foundations (in current architecture, pre-inversion).** Land the hash-derived protocol integer + negotiated support-range handshake with freeze-at-handshake and hard refuse on empty intersection. Fix the unknown-message policy (unknown event → marked+preserved; unknown RPC → hard error) — repairs a live "absence must be observable" violation regardless of endgame. Land the **locator-bundle** schema and the reserved **`replay`** actor value now (both additive capture-side changes) so every Action/event recorded from here on is forward-compatible. These are the time-sensitive, schema-rotting items.
2. **Move semantics into the extension.** Port the event store, history, Action model (record + clean + parameterize), redaction ownership confirmation, and the MCP tool definitions/dispatch into the extension. Reduce `server/src/mcp.js` to a passthrough. Add the domain-blind tripwire test.
3. **Deterministic replay engine + run journal** (the hardest correctness work): locator-bundle resolution, `on_failure` policies, redacted-value prompting, healing events.
4. **The GUI** (side panel, vanilla): record controls, Action list, history browser with select/delete, observation-mode first-run + pause, connection/install status. Do **not** start this before phases 1–3 are locked (it is the most visible, least upstream work — the classic trap).
5. **Native-messaging transport (#6).** Single host binary (Go/Rust/Zig or Node SEA) = MCP-lifecycle shim + native-messaging↔MCP framing + loopback HTTP server + config-writer. Extension `connectNative`; per-install endpoints + discovery; the extension tries native messaging and reports a precise actionable error if the host is absent (never a silent WS fallback). Installer for 3 OSes × 2 browser families.
6. **Store submission** (CWS + AMO): the calendar long pole. De-risk earlier per §4 (permissions). Optional-host-permissions model, listing assets, privacy policy.
7. **Later/optional:** #7 (extension-carried store-delivered host) once #6 is stable and review tolerance is measured; #8-relay as an opt-in second transport; rlsbl store-upload pipelines.

Two non-code long poles that no parallelism compresses: the store-review latency, and (if pursued) the capability request landing.

## 7. Effort estimate

Roughly a **v0.2 → v0.4 arc**, several focused sessions of subagent-fleet work for the code, plus two non-code long poles (store review; optional capability request). Per workstream (rough): protocol foundations (small-moderate); semantics migration (moderate, mostly moving verified logic across the wire); replay engine (moderate-large, the hardest correctness work); GUI (large, most new surface, needs design iteration on vanilla components); native-messaging host + installer (moderate-large, cross-platform + signing); store submission (little code, large calendar). Release **once at the very end** of the arc, not per phase.

## 8. External follow-up — the capability request (optional, high-leverage)

If a "client-listens / server-dials" MCP transport existed, the external component could drop to **zero**. Research findings (Aug 2026): no such transport exists or is on the roadmap (the 2026 roadmap explicitly adds no new official transports; the WebSocket SEP-1288 died dormant on the browser-can't-set-auth-headers objection), **but the spec's Custom Transports clause makes it fully legal** — it prescribes newline-delimited JSON-RPC over any bidirectional byte stream. So the ask is "implement a transport the spec already permits," a client feature, not a protocol fork. Anthropic's own Claude-in-Chrome ships exactly this bridge (see claude-code issues #27585, #81495), which is strong validating evidence.

- **Primary target:** a feature request on `anthropics/claude-code` — "MCP: client-listens local transport for always-on servers that can't be spawned or dialed (browser extensions)." Beats: topology gap → you already pay this cost (cite the two issues) → the spec already permits it (quote Custom Transports + the stdio "works over unix sockets/TCP" note) → concrete shape `{"type":"listen","path":"~/.claude/mcp/<name>.sock"}` (unix socket; OS file permissions are the auth, sidestepping the WS-SEP objection) → auth/DNS-rebinding pre-answered (0700 dir, same-user, one connection).
- **Secondary:** a comment (not a new SEP) on the deferred `modelcontextprotocol/modelcontextprotocol` PR **SEP-2598 (Pluggable Transports)** offering the browser-extension topology as a motivating case (a *topology* gap, stronger than the gRPC/SSH *preference* cases already there).
- Do **not** open a fresh transport SEP in core (roadmap forecloses it; SEP-2598 owns the space).
- Posting is an outward-facing action under the maintainer's GitHub identity — requires explicit go before firing.
